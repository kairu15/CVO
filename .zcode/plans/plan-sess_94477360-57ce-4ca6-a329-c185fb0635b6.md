# Admin Dashboard Overview — system-wide command center

## Context
`/dashboard/admin` currently renders a generic hero card, the dispersal map, the barangay widget and placeholder cards — it does not summarize the system. Goal: a professional, data-driven overview that surfaces KPIs, monitoring, beneficiary, field-visit, technician, geographic, dispersal-analytics, audit and report insights on one screen, built on **real data** from the existing modules, without breaking them.

**Exploration findings that shape the design:** there is no aggregate dashboard endpoint today; the richest reusable backend pieces are `ReportService::cityWide()` (program/activity/clinical/per_barangay/trend in one payload), `ReportChartService` (dispersalTrend, animalTypeDistribution, technicianWorkload…), the inline verification-counts query in `ReportController::verificationSummary()`, `BarangayDispersalAnalyticsService`, `DispersalMapService::snapshot()`, and `activity_logs`. Frontend has reusable primitives to promote: the `Stat` card, `ChartCard` + `useChart`, `CHART_COLORS/PIE_COLORS/AXIS_STYLE` (ReportsPage.jsx:46-143), `BarangayDispersalWidget`, the RoleDashboard map block (pinned by `DispersalMapMount.test.jsx`), plus card/eyebrow/grid conventions.

## Backend (Laravel)

1. **New `app/Services/DashboardService.php`** — `overview(User $viewer): array`, wrapped in `Cache::remember('dashboard:admin:v1', 60s)` (same pattern as `ReportController::cached()`). Sections:
   - `kpis` — beneficiaries_total, geo_tagged, technicians_active, field_visits_total + last_30_days, monitoring_records_total, dispersal_records_total (active `animal_ownership_events`).
   - `monitoring` — total records, distinct monitored households, livestock/poultry/unspecified split (join `animal_types.main_category`, legacy `animal_type` fallback), records-by-month (12 mo zero-filled).
   - `beneficiaries` — total / with_technician / unassigned (reuse `cityWide.program`), geo_tagged count, registrations-by-month (12 mo, `beneficiaries.created_at` — indexed), top barangays (reuse `cityWide.per_barangay`).
   - `field_visits` — verification counts (reuse, see #3), visits-by-month (12 mo), last-30-days count, `recent` 6 visits (date, farmer, technician, purpose, verification_status, has_photo).
   - `technicians` — totals {active, deactivated} + roster (≤12): assigned_households (`beneficiaries.technician_id`), completed visits total + last 30 days (`field_visits`), last sign-in (`users.last_login_at`), last visit date.
   - `dispersal` — counts by `event_type` from active `animal_ownership_events` + 12-mo trend (reuse `ReportChartService::dispersalTrend()`).
   - `distribution` — animal type distribution (reuse `ReportChartService::animalTypeDistribution()`).
   - `audit` — latest 8 `activity_logs` (action, actor name/role, target_type/id, created_at).
   - `generated_at`.
   Composition reuses `ReportService::cityWide()` and the chart services directly (their own caches keep nested calls cheap); only the genuinely missing aggregates are new focused queries.
2. **Extract** the verification-counts grouped query from `ReportController::verificationSummary()` into `FieldVisitVerificationService::summaryCounts()`; `ReportController` calls it (single source of truth for "needs review").
3. **New `app/Http/Controllers/DashboardController.php`** — `index(Request)` → `{'data': …}`; second gate `abort_unless($user->hasPermission('view_reports'), 403)` mirroring the admin-group convention.
4. **Route** (routes/api.php admin group, before `/admin/report`): `GET /admin/dashboard` → `DashboardController@index` with `->middleware('permission:view_reports')`. No new capability key — the overview is a program-report surface and the existing matrix governs it.
5. **Tests** — `tests/Feature/DashboardOverviewTest.php` (pattern of `ReportTest.php`): admin 200 with every section key + correct aggregates on seeded fixtures; guest 401; technician 403 under the shipped seed; technician 200 after granting `view_reports` via `role_permissions`.

## Frontend (React)

1. **`src/api/dashboardApi.js`** (new) — `overview()` → `GET /api/v1/admin/dashboard` (90s timeout, like reportsApi). Add `useDashboardOverview()` to `src/api/queries.js` (key `["dashboard","overview"]`, staleTime 30s, refetchInterval 60s to match the server cache).
2. **Promote shared primitives** (avoid duplication): `src/components/StatCard.jsx` (from ReportsPage's `Stat`, plus optional icon/link/tone), `src/components/ChartCard.jsx` + `src/hooks/useChart.js`, `src/lib/charts.js` (CHART_COLORS/PIE_COLORS/AXIS_STYLE), `src/lib/auditLabels.js` (ACTION_LABELS/labelFor from AuditLogPage). `ReportsPage.jsx` and `AuditLogPage.jsx` refactored to import them — same rendered DOM, so their tests stay green.
3. **Extract the dashboard map block** from `RoleDashboard.jsx` into `src/components/DashboardOverviewMap.jsx` (same wiring: `mapApi.dates/pins`, abort/token race guard, `useAutoRefresh`, `DispersalMap flightPathsOnly` + `BarangayChoropleth showLabels labelShowCounts`). `RoleDashboard` (now the technician dashboard) renders the shared component — **`DispersalMapMount.test.jsx` keeps passing unchanged**.
4. **New `src/pages/AdminOverviewPage.jsx`** — sections in order:
   - Header: eyebrow + title, "Data as of {generated_at}" + manual refresh.
   - **KPI band** — 6 linked StatCards (Beneficiaries, Active technicians, Field visits 30d, Monitoring records, Dispersal records, Visits needing review → deep link `?verification=review`).
   - **Monitoring Overview** — stat trio (records, monitored households, livestock/poultry split) + records-by-month bar chart → link to Monitoring.
   - **Beneficiary Overview** — totals (assigned/unassigned/geo-tagged) + registrations-by-month chart + top-barangay table → link.
   - **Field Visit Activities** — verification chips + visits-by-month trend + recent-visits list with `VerificationBadge` → link.
   - **Technician Performance** — roster table (households, visits, last-30-days, last sign-in) + workload bar → link.
   - **Geographical Overview** — `<DashboardOverviewMap />` + coverage hint → link to Map.
   - **Barangay Dispersal Analytics** — reuse `<BarangayDispersalWidget roleKey="admin" />` as-is → link.
   - **Recent System Activities** — audit feed (labeled actions, actor, relative time) → link to Audit.
   - **Reports & Analytics** — dispersal-trend line + animal-type donut (shared `ChartCard`s) → link to full Reports (avoid duplicating the whole Reports page).
   - Every section: `card`/`eyebrow` conventions, `SkeletonList` loading, `InlineAlert` + retry on error, `EmptyState` on zero data, responsive grids (`gap-3 sm:grid-cols-2 lg:grid-cols-4` etc.).
5. **Routing** — `routes/index.jsx`: `/dashboard/admin` → lazy `AdminOverviewPage` inside `RoleRoute dashboard="admin"`. `RoleDashboard` keeps serving the technician dashboard.
6. **Tests** — new `src/test/AdminOverviewPage.test.jsx` (mocked `dashboardApi`/`mapApi`): KPI values, section rendering, links, loading/error/empty states. Update `e2e/dashboards.mjs`: add an `/api/v1/admin/dashboard` stub fixture and replace the stale `/Pinned locations/` assertion with text the new page actually renders.

**Not touched:** all 8 module pages (links only), the map/analytics endpoints, mobile app, permissions matrix.

## Verification
1. Backend: `php artisan test --testsuite=Feature` (new DashboardOverviewTest + full suite green).
2. Frontend: `npx vitest run` (new page test + existing suites, incl. DispersalMapMount, BarangayDispersalWidget, ReportsPage, AuditLogPage) and `npx vite build`.
3. Live smoke test: `php artisan serve` + `npm run dev`, then browser-verify `/dashboard/admin` renders all sections with real dev data, quick-links navigate correctly, and the module pages still work (browser-use skill).
4. Optional: `node e2e/dashboards.mjs` if both servers are up.
